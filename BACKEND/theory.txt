# Backend Theory

## 1. Creating the Server and User Authentication APIs

The backend is the server-side part of an application that handles client requests, processes business logic, communicates with the database, and sends responses back to the frontend. In this project, **Node.js** is used as the runtime environment, **Express.js** is used to create the server and APIs, and **MongoDB** is used as the database with **Mongoose** as the ODM (Object Data Modeling) library.

### 1.1 `app.js` and `server.js`

The backend application is divided into `app.js` and `server.js` to keep the application configuration and server startup separate.

**`src/app.js`** is responsible for creating the Express application instance. It is also used to configure middleware and register different routes of the application. Middleware processes requests before they reach the appropriate route, while routes define how the server responds to different API requests.

**`server.js`** is the entry point used to start the backend server. It imports the Express application created in `app.js`, establishes the database connection, and starts listening for incoming requests on a specified port.

Therefore, the basic responsibility is:

**`app.js` → Configure the application**

**`server.js` → Start the server**

This separation makes the backend easier to organize, maintain, and scale as more features are added.

# 2. Creating MongoDB Atlas Cluster

MongoDB Atlas is a cloud-based service used to host MongoDB databases. Instead of running MongoDB only on the local computer, Atlas allows the database to be hosted on the cloud and accessed by the backend application.

A **cluster** is the MongoDB deployment that provides the environment in which databases and collections are stored. For this project, a development/free-tier cluster is created in MongoDB Atlas.

After creating the cluster, database access is configured by creating a database user with a username, password, and appropriate permissions. These credentials are required when the backend application connects to MongoDB.

---

## 2.1 IP Access List

MongoDB Atlas uses network access rules to control which IP addresses are allowed to connect to the database.

An IP address can be added to the IP Access List to allow a particular system to connect to MongoDB.

The entry **`0.0.0.0/0`** allows connections from any IPv4 address. This can be useful during development, but it is not recommended as a general production configuration because it increases the network exposure of the database.

---

# 3. MongoDB Connection String

MongoDB Atlas provides a connection string that contains the information required to connect an application to the MongoDB cluster.

The connection string generally contains:

* Database username
* Database password
* Cluster address
* Database name

The backend uses this connection string to establish a connection with MongoDB.

The connection string can also be used in MongoDB Compass to visually access and manage the database.

For security, the connection string should not be directly written inside the source code. It is normally stored in an environment variable such as `MONGODB_URI`.

---

# 4. Connecting MongoDB with the Backend

A separate database configuration file, such as `src/config/database.js`, is created to handle the MongoDB connection.

The **Mongoose** package is used to establish the connection between the Node.js application and MongoDB.

A `connectDB()` function is created for this purpose. The function attempts to connect to MongoDB and uses `try-catch` to handle successful and failed connection attempts.

The connection process can be represented as:

**Backend → Mongoose → MongoDB Atlas → Database**

The database connection function is imported into `server.js` and executed when the backend starts.

This keeps database-related code separate from the main server configuration and makes the project easier to maintain.

---

# 5. Creating the User Model

After connecting the database, the next step is to define how user data will be stored.

A **User Schema** is created inside the `models` folder. A schema defines the structure and properties of the user document, such as name, email, and password.

The schema is then converted into a **Mongoose Model**.

The model provides methods that allow the backend to perform operations on user documents in MongoDB, such as creating, finding, updating, and deleting users.

The relationship can be understood as:

**Schema → Model → MongoDB Collection → User Documents**

For authentication systems, passwords should never be stored as plain text. They should be securely hashed before being stored in the database.

---

# 6. Creating Authentication Routes

After creating the User Model, routes are created to define the APIs responsible for authentication.

A separate `routes` folder is created to organize the API routes. For authentication, a file such as `auth.routes.js` is created.

Express Router is used to create a separate router for authentication-related APIs.

Common authentication APIs include:

* **POST `/register`** – creates a new user account.
* **POST `/login`** – verifies user credentials and authenticates the user.
* **POST `/logout`** – terminates the user's authenticated session.

Using separate route files keeps the backend organized and prevents all API definitions from being placed inside `app.js`.

---

# 7. Route Prefix

A common prefix can be assigned to authentication routes in `app.js`.

For example, if the prefix is:

`/api/auth`

and the router contains:

`/register`

the final API endpoint becomes:

`/api/auth/register`

Similarly, a login route becomes:

`/api/auth/login`

A route prefix provides a common structure for related APIs and makes the API architecture easier to understand and maintain.

---

# Overall Backend Architecture

The complete flow of the backend developed so far is:

**Client → Express Server → Routes → Authentication Logic → User Model → Mongoose → MongoDB Atlas**

When the server starts:

**`server.js` → Connect to MongoDB → Start Express Server**

When a user sends an authentication request:

**Frontend → Authentication API → Route → User Model → MongoDB → Response**

This structure provides a clear separation between server configuration, routing, database communication, and user authentication logic.
